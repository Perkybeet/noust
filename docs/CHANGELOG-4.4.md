# Noust 4.4 changelog

Changes since Noust 4.3.0. What to do before updating is in [UPGRADING-4.4.md](UPGRADING-4.4.md).

## Before you upgrade

[UPGRADING-4.4.md](UPGRADING-4.4.md) has the order of an update and the way back; this is what to know first.

- **The update takes the image pull of before 3.2.1 out of the unit of a Compose stack that still has it.** One
  exact line, with or without `-p`, in a unit that carries `# Generated by Noust`; nothing restarts, and the
  step says so and writes `compose.pull_removed` in the audit trail
  ([UPGRADING-4.4.md](UPGRADING-4.4.md#the-image-pull-of-before-321-leaves-the-unit)).

## The start of a Compose stack

What was left over from the check that holds a stack's start to what was judged (4.3.0, the first item of
[Security](CHANGELOG-4.3.md#security)).

- **A stack whose compose file does not resolve is taken from its containers.** When Docker Compose cannot
  resolve a stack's file (or it is not there) and Docker answers with containers of the stack, the step that
  brings stacks under the check writes the record from what the containers were given, takes the project from
  their labels and puts the check in the unit. A stack with no container, or with Docker not answering, stays
  as it was, and `noust health` says so with how many days it has waited; from the seventh day it is also in
  what needs attention
  ([UPGRADING-4.4.md](UPGRADING-4.4.md#compose-stacks-noust-could-not-take-over)).
- **A stack with no record has its containers and nothing else.** An update, a redeploy and an edit in the Docker
  zone no longer read what a stack "already had" from the compose file at the commit that served or from the file
  on disk, which whatever mounts the tree can write. The helpers that only read that history (the links an update
  changed and what it left unchanged) are gone.
- **`noust health` says when a unit is not the one Noust wrote.** A unit that carries `# Generated by Noust` and
  starts something else (somebody edited it and left the line) is named, with how to mend it; an addition of the
  unit that replaces or adds to `ExecStart=` is named with its path, as the ones that empty `ExecStartPre=` were.
  Noust touches neither.
- **What is to be looked at about how the stacks start has a line of its own in `noust health`**, `Compose
  stacks`, and no longer shares the build sandbox's. The shape of `GET /api/system/health` and of `noust health
  --json` is the same.

## Backups

- **Two passes that send the copies that wait do not send the same one twice** (item 201). When the timer and a
  pass run by hand met, or two timers after a network cut, both could upload the same copy and both tell of it.
  A pass now claims each copy for its destination before it sends it and the other leaves it; `noust backup resend`
  and its `--json` say how many were left to the other pass (`busy`).

## Diagnosing

- **A container that the kernel killed for memory is looked for where it ran** (item 175). For a Compose stack
  or a container application, `noust app diagnose` read the memory events of the unit that starts the stack, which
  holds no process. It asks Docker how each container ended and reads the container's own counters; for a stack
  the cause names the compose file, since its limits are written there.
- **"Degraded" is only said with the cause that explains it.** A certificate past the day it should have been
  renewed, a unit left over or an idle copy of a blue/green pair, and a unit in a state that is neither running
  nor stopped make an application degraded, each with its sentence as the cause. A warning with nothing to do
  about it (a log with no date, a disk between 90 and 95 %) is listed and does not change the verdict.

## Where an application answers

- **`NOUST_URL`, `{{app.URL}}` and the address a code host shows are where the application answers on that
  machine.** They were always `https://` and the application's name, also where there is no site and no
  certificate: a central that deploys on its own machine answers at the machine and a port. They ask the same
  thing the card at the end of a deployment and a recipe's notes ask.
- **The address card and `noust status` reach a static or PHP site by its name.** On a server they said it served
  no web, because it has no port; they ask the same answer as the variable now, so the card, the variable and
  the status of a code host cannot disagree.
- **The status a central writes on GitHub for a deployment on a server carries the address the server says.**
  The application is on the server, whose edge decides where it answers (its machine and a port where it has no
  site), and the central cannot say it for a machine that is not its own: when the deployment succeeded it asks
  the server's address card, and keeps the one it recorded when a server before 4.3 has none.

## Fleet

- **`noust node host-key NAME` accepts the new SSH host key of a server.** When a server's key changes the
  central closes the tunnel and says so, and the only way on was to remove the server and add it again. The
  command shows the key the central kept and the one the server presents now and goes on only with the
  fingerprint typed or given (`--fingerprint SHA256:...`); there is no way to accept it unseen. The API has it
  as two operations, the second in sudo mode ([CENTRAL.md](CENTRAL.md)).
- **Accepting that key waits for a second person where `noust node rekey` does.** It decides which machine the
  central connects to, as a new key does. The fingerprint is part of the call that is approved, so whoever decides
  sees the one that will be accepted, an approval for one fingerprint takes no other, and the central compares it
  again with what the server presents when the call runs ([Sudo mode and four-eyes
  approvals](security-approvals.md#four-eyes-approvals)).

## Adopting

- **What adopting a stack warns about is said in the console's language**: a checkout with changes nobody
  committed, a stack with no site or with one that is not enabled, and a port published only on this machine.
  The lines about what a restart of the machine would leave down (a container stopped, or whose restart policy
  does not bring it back) are sentences too.

## Fixes

- **A passkey that kept being refused with "A request is already pending" is said with its cure, and does not
  come back** (item 202). 4.3 asked the browser again a few times; that does not help where a password manager's
  extension answers for the browser and leaves open the request of the sign-in page's name field: every passkey
  after it was refused for as long as the page lived, the confirmation of a delicate action included. The
  message now says that reloading the page closes it, with the button beside it, and a browser that was seen
  leaving that request open is no longer offered passkeys in the name field, so the next sign-in leaves nothing
  open ([troubleshooting-sign-in.md](troubleshooting-sign-in.md#the-browser-says-another-passkey-request-is-still-open)).
