# Upgrading to 3.0: WASM becomes Noust

This guide is written against WASM 2.3. Earlier 2.x releases upgrade the same way; read the
2.x sections of [UPGRADING-2.0.md](UPGRADING-2.0.md) for what each of them changed on the
way. A 1.x server goes to 2.3 first.

The short version: 3.0 renames the product, and nothing you deployed notices. The command
is `noust`, the configuration and data move to `/etc/noust`, `/var/lib/noust` and
`/var/backups/noust`, and Noust's own systemd units are called `noust-*`. The move is done
by Noust itself, once, and leaves symbolic links at the old paths. Your applications keep
running throughout: their units, directories, sites, domains and certificates are not
touched. `wasm` keeps working as another name for `noust` for the whole 3.x series, so
scripts and cron lines that call it need no change.

## What changes

### The name and the command

- **`noust`** is the command. `wasm` runs the same program until 4.0. Typed by a person at a
  terminal, it says once, on standard error, that the product is now Noust; a script, a cron
  line or `--json` output never sees that notice. `noust --version` prints
  `Noust 3.0.x (formerly WASM)`.
- **The packages** are called `noust`: on PyPI, and in the `home:Perkybeet` repository for
  apt, dnf and zypper (the same repository WASM came from). The names WASM was published
  under, `wasm` (Debian, Ubuntu) and `wasm-cli` (Fedora, openSUSE, PyPI), are transitional
  packages in 3.x: each one contains nothing and depends on `noust` at the same version, so
  the upgrade command you already use brings `noust` in. The details per channel are in
  [RENAME.md](RENAME.md).
- **The Python package** is `noust`. Code that imported `wasm` must import `noust`.
- **The console** is called Noust: its logo, titles and texts. Its address, its access token,
  its sessions and your two-factor enrolment are the same. It tells each browser once that
  WASM is now Noust.
- **The repository** is `github.com/Perkybeet/noust`. GitHub redirects the old address.
- **`man noust`** replaces `man wasm`.

### The paths

| Until 2.3 | From 3.0 | What it holds |
|---|---|---|
| `/etc/wasm` | `/etc/noust` | `config.yaml`, the console's state (signing key, token hash, sessions, 2FA, audit log) |
| `/var/lib/wasm` | `/var/lib/noust` | the store, deploy and job logs, `secrets/`, the monitor's observations |
| `/var/lib/wasm/wasm.db` | `/var/lib/noust/noust.db` | the store itself, renamed inside the moved directory |
| `/var/backups/wasm` | `/var/backups/noust` | backup archives |
| `/etc/nginx/wasm-upstreams` | `/etc/nginx/noust-upstreams` | the upstreams of blue/green applications |
| `~/.local/share/wasm` | `~/.local/share/noust` | the store of an unprivileged run, per user |
| `/var/log/wasm` | `/var/log/noust` | Noust's own log files |

Every old directory except `/var/log/wasm` is left as a symbolic link to the new one, so
anything that reads `/etc/wasm/config.yaml` or copies `/var/backups/wasm` still finds it.
Write new scripts against the new paths: the links are there for the transition.

The logs are not moved. Noust writes its own log files to `/var/log/noust` from 3.0 on, and
`/var/log/wasm` stays as it was, with WASM's logs in it, until you remove it.

### Environment variables

`NOUST_APPS_DIR`, `NOUST_WEBSERVER`, `NOUST_SERVICE_USER`, `NOUST_SSL_EMAIL` and
`NOUST_WEB_STATE_DIR` are read first; the `WASM_` spellings are still read when the `NOUST_`
one is not set.

### Noust's own units

| Until 2.3 | From 3.0 |
|---|---|
| `wasm-web.service` | `noust-web.service` |
| `wasm-monitor.service` | `noust-monitor.service` |
| `wasm-cron-<name>.service`, `.timer` | `noust-cron-<name>.service`, `.timer` |
| `wasm-backup-<app>.service`, `.timer` | `noust-backup-<app>.service`, `.timer` |
| `wasm-previews.service`, `.timer` | `noust-previews.service`, `.timer` |

Units written by Noust say "Generated by Noust" in their header; Noust recognises both that
and WASM's "Generated by WASM".

### The API

- The same endpoints, error shape and scopes. `GET /health` reports
  `"service": "noust-web"`.
- New API tokens start with `noust_tok_`, and a new master access token with `noust_`. Tokens
  issued by WASM (`wasm_tok_`, `wasm_`) keep working until you revoke or replace them.
- `GET /api/services` takes `noust_only`; `wasm_only`, its name before 3.0, is still read
  when `noust_only` is absent.
- `GET /api/auth/session` reports `renamed_from_wasm` on a server that ran WASM.
- Kept as they were, so that nothing already running breaks: the cookies `wasm_session` and
  `wasm_csrf`, the `X-WASM-CSRF` header, and the WebSocket subprotocols `wasm.auth` and
  `wasm.token.<token>`.

### What does not change

- **Your applications.** Their units keep their names (`<app_name>.service`, and the `wasm-`
  prefix of units deployed before WASM 0.14.1, which is part of the application's name, not
  of the product's), and so do their directories under `/var/www/apps`, their nginx or Apache
  sites, their domains, aliases and redirects, their certificates, their `.env` files and
  their releases. Nothing an application runs is restarted by the upgrade.
- **Files inside applications and repositories.** `.wasm/`, `.wasm-runtime.json`,
  `.wasm-php.json` and `.wasm-php-tmp` keep their names. A repository's nginx overrides may
  be called `noust.nginx.yaml`; `wasm.nginx.yaml` is still read.
- **Backups.** They move with `/var/backups/wasm`, and every record of them stays valid.
  Archives keep their internal layout, remote destinations keep their `wasm-backups` folder,
  and their credentials and encryption keys are unchanged.
- **Exports.** `noust app export` still writes the `wasm-app` format, and a file exported by
  WASM 2.3 imports into Noust.
- **Databases.** The read-only roles and accounts keep their `wasm_ro_<database>` names.
- **Tokens, sessions, two-factor authentication, webhooks and the GitHub App.** Hook URLs,
  secrets and the App's key are unchanged.
- **Configuration.** Every value you set is kept. The migration rewrites only three values,
  and only where they still hold WASM's default: `backup.directory` (`/var/backups/wasm`),
  `logging.file` and `monitor.log_file` (under `/var/log/wasm`). A path you chose stays yours,
  and keeps working through the links.

## The migration

`noust migrate-from-wasm` moves a WASM server onto Noust's names. It also runs by itself:

- **From the packages.** The apt, dnf and zypper packages run it at the end of the upgrade,
  so on those channels the server has moved by the time the upgrade returns.
- **On the first command run as root.** Any `noust` or `wasm` command run as root, while
  anything of WASM's is left to move, migrates first and then does what you asked. It
  announces each step. It does not run inside a systemd unit (the console's own unit, a
  cron or backup job), under `--dry-run`, during shell completion, or when
  `NOUST_NO_AUTO_MIGRATE=1` is set; the explicit command always runs.

What it does, in order, under a lock (`/run/noust-migrate-from-wasm.lock`; a second run
waits for the first):

1. **The directories are renamed**: `/etc/wasm`, `/var/lib/wasm`, `/var/backups/wasm` and
   root's `~/.local/share/wasm`, each with a single rename(2) and a symbolic link left at
   the old name. Nothing is copied. When an old and a new name are on different filesystems
   the step is refused and explained, and Noust keeps using the old directory where it is.
2. **The store is renamed** from `wasm.db` to `noust.db`, after folding its write-ahead log
   into it. `wasm-web` and `wasm-monitor`, which hold it open, are stopped for the rename
   and started again afterwards. If another process still has it open, the rename is
   refused: stop that process and run `noust migrate-from-wasm`. A new, empty store is never
   created beside an old one, so the "No applications deployed" surprise of a store read from
   the wrong place does not happen here.
3. **The configuration**: the three default paths above, edited as text so your comments and
   ordering survive.
4. **The blue/green upstream directory** is renamed to `/etc/nginx/noust-upstreams`, with a
   link at the old name, and the sites that include it are repointed. nginx is tested before
   it is reloaded; if the test fails, the sites are put back and keep working through the
   link.
5. **PHP-FPM pools** WASM wrote as `wasm-<app>` become `noust-<app>`, with their sockets. The
   new pools are added beside the old ones, FPM reloaded, the sites repointed, nginx tested
   and reloaded, and only then are the old pools removed, so no request is dropped. When a
   test fails, everything is put back. Pools written from 3.0 on are `noust-<app>` from the
   start.
6. **Noust's own units** are replaced, one unit (with its timer) at a time: the same unit is
   written under its `noust-*` name, pointing at `noust` and the new paths, enabled if the old
   one was enabled, and started if the old one was running, and it must stay up. Only then is
   the old one disabled and removed. When a step fails, the new unit is removed and the old
   one put back, enabled and started as it was. A cron or backup job that is running at that
   moment is left alone until the next run. Units are only replaced once the directories
   have moved.

Each step looks at what is on disk, so a run that was interrupted, or refused a step, is
finished by running it again. What was done is recorded in
`/var/lib/noust/migrated-from-wasm.json`.

```bash
noust migrate-from-wasm --dry-run          # what it would do, or what earlier runs did
noust migrate-from-wasm                    # do what is left
noust migrate-from-wasm --json             # the same, for a script
```

## Upgrading a production server

Upgrading does not stop or restart any application. The console and the monitor restart
once, under their new unit names.

### 1. Take stock

```bash
wasm --version                               # 2.3.x
wasm list                                    # keep this output to compare afterwards
wasm store path                              # where the store is
wasm web status
systemctl list-units 'wasm-*' --all          # WASM's units, and legacy application units
systemctl list-unit-files 'wasm-*' --state=enabled --no-legend | awk '{print $1}' \
  > /root/wasm-enabled-units.txt             # what to enable again if you roll back
systemctl list-timers 'wasm-*'               # scheduled backups and cron jobs about to run
for d in /etc/wasm /var/lib/wasm /var/backups/wasm; do mountpoint "$d"; done   # "is not a mountpoint"
```

WASM's directories are renamed, not copied, so each has to be on the same filesystem as its
new name. That is the case unless one of them is a mount point of its own (a separate disk
for backups, say); the migration then leaves that one where it is, Noust keeps using it
there, and the dry run says how to move it yourself.

**Running jobs.** A deploy, update or restore started from the console runs inside the
console's process, and the console restarts during the upgrade: a job still running then is
marked failed ("Interrupted by a panel restart"). Wait until none is running: the console's
activity page, or `GET /api/jobs?status=running`. Avoid upgrading while a scheduled backup
is due, and do not start `wasm` commands in another session meanwhile.

### 2. Back up

```bash
install -d -m 700 /root/wasm-2.3-backup
cp -a /etc/wasm /root/wasm-2.3-backup/etc-wasm             # configuration and console state
cp -a /var/lib/wasm /root/wasm-2.3-backup/var-lib-wasm     # the store, logs, secrets/
wasm store export -o /root/wasm-2.3-backup/store.json      # every record, readable
install -d -m 700 /root/wasm-2.3-backup/units
cp -a /etc/systemd/system/wasm-* /root/wasm-2.3-backup/units/
```

If `wasm store path` printed a location outside `/var/lib/wasm`, copy that directory too.
`/var/backups/wasm` is not copied: the migration renames it in place and never rewrites an
archive.

Keep a way to reinstall 2.3.x:

- **Debian and Ubuntu:** the `.deb` is attached to the GitHub release
  `https://github.com/Perkybeet/noust/releases/tag/v2.3.0` (`wasm_2.3.0-1_all.deb`).
- **Fedora and openSUSE:** OBS publishes only the latest build. Save the installed package
  before upgrading, while the repository still serves it: `dnf download wasm-cli`, or copy
  it from the zypper cache.
- **PyPI:** `pip install 'wasm-cli==2.3.0'` stays available.

### 3. Upgrade the package

```bash
apt update && apt upgrade                    # Debian, Ubuntu (or: apt install noust)
dnf upgrade --refresh                        # Fedora
zypper refresh && zypper update              # openSUSE
pip install -U 'noust[all]' wasm-cli         # PyPI: both in one step
```

- **apt**: `apt upgrade` turns `wasm` into the transitional package, which brings `noust`
  in. `apt-get upgrade` never installs a new package and reports `wasm` as kept back: use
  `apt upgrade`, `apt-get dist-upgrade` or `apt install noust`. `apt autoremove` later
  removes the empty `wasm` and keeps `noust`.
- **dnf, zypper**: `wasm-cli` 2.x is replaced by the transitional `wasm-cli`, which requires
  `noust`. To remove the transitional package later on Fedora, mark `noust` as wanted
  first: `dnf mark user noust && dnf remove wasm-cli`.
- **pip**: upgrading `wasm-cli` together with `noust` keeps the `wasm` command.
  `pip uninstall wasm-cli` later removes `bin/wasm` even though `noust` provides it too; put
  it back with `pip install --force-reinstall --no-deps noust`. With pipx:
  `pipx uninstall wasm-cli && pipx install noust`. With pip, nothing migrates until the first
  command run as root, so you can read `noust migrate-from-wasm --dry-run` first.

The distribution packages ship no configuration under `/etc`; the default configuration is a
reference at `/usr/share/noust/config.example.yaml`. Your `/etc/wasm/config.yaml` is kept
through the package change and moved by the migration.

### 4. Check

```bash
noust --version                              # Noust 3.0.x (formerly WASM)
noust migrate-from-wasm --dry-run            # what was done; nothing may be left to do
noust list                                   # the same applications, in the same states
noust status shop.example.com                # for a few applications
noust web status                             # the console, as noust-web.service
noust store path                             # /var/lib/noust/noust.db
systemctl list-units 'noust-*' --all         # every unit that was wasm-* in step 1, renamed
systemctl list-timers 'noust-*'              # the same schedules, next runs included
systemctl list-units 'wasm-*' --all          # only legacy application units, if any
ls -ld /etc/wasm /var/lib/wasm /var/backups/wasm    # links to the new paths
noust health
```

If the dry run lists steps "not done", read the reason under each, fix it, and run
`noust migrate-from-wasm`. If `noust list` says no applications are deployed, the records
are not lost. Stop, compare `noust store path` with what you noted in step 1, and look at
`ls -la /var/lib/noust /var/lib/wasm` before doing anything else.

Sign in to the console with the same token as before and check that every application
appears with its state. If you use notifications, send a test: `noust notify test <channel>`.

### 5. Scripts, cron lines and automation

- Everything that calls `wasm` keeps working in 3.x. Change it to `noust` at your pace.
- Anything that names WASM's units (`systemctl status wasm-web`, a monitoring check on
  `wasm-backup-shop-example-com.timer`) must use the `noust-*` names: the old units no longer
  exist.
- Anything that reads the old paths keeps working through the links, except
  `/var/log/wasm`, which no longer receives new lines.
- Code that imports the `wasm` Python package must import `noust`.

## Rolling back the upgrade

Going back to 2.3 means putting back three things: the program, the store and configuration
WASM kept in `/etc/wasm` and `/var/lib/wasm`, and WASM's units under their old names.
Everything done under 3.0 (deploys, new applications, new cron jobs or schedules) is not in
the records you restore.

Do not reinstall 2.3 and stop there: `/var/lib/wasm` is now a link to `/var/lib/noust`,
where the store is called `noust.db`, and 2.3 looks for `wasm.db`. It would start with an
empty store and report no applications. The records are not lost; step 3 puts the store
back where 2.3 reads it.

1. **Stop the console:** `noust web stop`.

2. **Reinstall 2.3.x:**

   ```bash
   apt remove noust && apt install ./wasm_2.3.0-1_all.deb          # Debian, Ubuntu
   dnf remove noust && dnf install ./wasm-cli-2.3.0-*.noarch.rpm   # Fedora, the package you saved
   zypper remove noust wasm-cli && zypper install ./wasm-cli-2.3.0-*.noarch.rpm   # openSUSE
   pip uninstall noust wasm-cli && pip install 'wasm-cli[all]==2.3.0'            # PyPI
   ```

   Removing the `noust` package (and with it the transitional package that requires it)
   stops and disables `noust-web` and `noust-monitor`; it removes no data.

3. **Put the store and configuration back.** Restore the copies from step 2 of the upgrade,
   and keep the 3.0 directories aside:

   ```bash
   ls -ld /etc/wasm /var/lib/wasm                  # both must be symbolic links
   rm /etc/wasm /var/lib/wasm                      # removes the links only
   mv /etc/noust /etc/noust.3.0
   mv /var/lib/noust /var/lib/noust.3.0
   cp -a /root/wasm-2.3-backup/etc-wasm /etc/wasm
   cp -a /root/wasm-2.3-backup/var-lib-wasm /var/lib/wasm
   ```

   `/var/backups/wasm` stays a link to `/var/backups/noust`, which 2.3 reads through; leave
   both in place.

4. **Put WASM's units back under their old names.** 2.3 knows only the `wasm-*` names, and
   the `noust-*` units start a program that is no longer installed:

   ```bash
   cd /etc/systemd/system
   for f in noust-*.service noust-*.timer; do
       [ -f "$f" ] && grep -q "Generated by Noust" "$f" || continue
       systemctl disable --now "$f"
       rm "$f"
   done
   cp -a /root/wasm-2.3-backup/units/. /etc/systemd/system/
   systemctl daemon-reload
   xargs -r systemctl enable --now < /root/wasm-enabled-units.txt
   ```

   The loop removes only units Noust generated for itself. If one of your applications has a
   name that begins with `noust-` (a domain like `noust-example.com`), its unit may match the
   pattern too: leave it out of the loop.

5. **Blue/green applications.** Their sites include `/etc/nginx/noust-upstreams`, and
   `/etc/nginx/wasm-upstreams` is a link to it, so they keep serving and 2.3 writes to the
   same files through the link. Leave both in place.

6. **PHP-FPM applications.** Their pools keep serving under the `noust-` names 3.0 gave
   them. Redeploy each with 2.3 (`wasm update DOMAIN`), which writes its pool and its site
   again under the `wasm-` name, then remove the `noust-<app>.conf` pool left behind in the
   PHP-FPM pool directory (`/etc/php/<version>/fpm/pool.d` on Debian and Ubuntu,
   `/etc/php-fpm.d` on Fedora and openSUSE) and reload PHP-FPM.

7. **Check** with `wasm --version`, `wasm list`, `systemctl list-units 'wasm-*' --all` and
   `systemctl list-timers 'wasm-*'`, then start the console as before (`wasm web enable`
   with your options, if the loop did not already).

What does not come back:

- **Applications created or redeployed under 3.0** are missing from, or older in, the
  restored store. Their units, sites and releases keep serving; redeploy them with 2.3 to
  record them again.
- **Backups taken under 3.0** stay in `/var/backups/noust`, which `/var/backups/wasm` still
  points at, but the restored store has no record of them.
- **API tokens issued under 3.0** (`noust_tok_`) are not in the restored configuration.
- Deployment history, jobs and audit entries recorded under 3.0, kept in
  `/var/lib/noust.3.0` and `/etc/noust.3.0`.
