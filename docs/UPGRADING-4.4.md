# Upgrading to 4.4

This guide is written against Noust 4.3.0. A server older than 4.3 reads [UPGRADING-4.3.md](UPGRADING-4.3.md)
first. The whole list of changes is in [CHANGELOG-4.4.md](CHANGELOG-4.4.md).

The short version: 4.4 does not touch what serves your applications. No site, application or Compose stack is
restarted or recreated by the update. The units of the Compose stacks may be written once more
(a `daemon-reload` and nothing else), and `noust health` says more about how they start.

## What you will notice

Most of this is about the Compose stacks that 4.3 left in a state it could not mend by itself, and about
what `noust health` says of how a stack starts. It is what the step that runs at the update
(`noust setup compose-gate`) does, and the console runs it again a little after it starts and every ten
minutes.

- **A stack Compose cannot resolve is taken from its containers.** In 4.3 a stack whose compose file `docker
  compose config` could not resolve when the step reached it (the file was being replaced, a variable was
  missing, the file is not valid) was left as it was, with no record of what it was accepted with, and an
  update of it was judged against the compose file the tree served. 4.4 takes such a stack when Docker answers
  and it has containers: what they were given is what it is accepted with, the project is the one on their
  labels (the one Noust already recorded wins, and two projects in the tree are not guessed between), and its
  unit gets the check of its start. A compose file that then asks for more than the containers have is held
  back at its next start, which is the check doing its job. [Compose stacks Noust could not take over](#compose-stacks-noust-could-not-take-over).
- **A stack with no record has its containers and nothing else.** An update or a redeploy of a stack that was
  never taken over no longer reads what it "already had" from the compose file at the commit that served or from
  the file on disk: whatever mounts the tree can write both. A stack that runs has a record after the first pass
  of the step; one that does not run and was never taken over is judged like a new stack, which asks for the
  recorded exception (`noust app sandbox compose-exception`) if its file asks for something of the server.
- **The pull of before 3.2.1 leaves the unit.** [Below](#the-image-pull-of-before-321-leaves-the-unit).
- **`noust health` says three more things.** A stack that has waited seven days to be taken over is listed with
  what needs attention (the bell, Home and a fleet's list); a unit that carries the `# Generated by Noust`
  line but starts something that is not what Noust writes is named, with how to mend it; and an addition of the
  unit that replaces `ExecStart=` is named with its path. Everything about how the stacks start has a line of
  its own, `Compose stacks`, and not the one of the build sandbox. The answer of `GET /api/system/health` and
  of `noust health --json` has the same shape: one more check, with its name.

Three more things, outside the stacks:

- **On a central that deploys on its own machine, `NOUST_URL` changes at each application's next deployment**,
  from `https://` and its name to where it answers there (`http://`, the machine and its port). An application
  that built links from that variable builds them to an address that works.
- **`noust app diagnose` says "healthy" where it said "degraded" with no cause.** Whoever reads `verdict` from
  `--json` or from the API sees the change; the warnings are still listed.
- **`noust backup resend --json` has one more field**, `busy`: the copies another pass was already sending.
- **Accepting a server's new SSH host key waits for a second person where approvals are on.**
  `POST /api/nodes/{node}/host-key` answers `202` with `approval_required`, like `rekey` does, and runs when
  the same call is made again with the approval; a script that accepted a key in one call needs the approval
  first. At the terminal, as root, `noust node host-key` is unchanged.
- **The address card says a static or PHP site is reached by its name.** `GET /api/apps/{domain}/address` and
  `noust status` said it served no web (`kind: none`); they say `site` with its address now.

Check: run `noust setup compose-gate`, then `noust health`. Every stack is under the check
(`grep -c "app compose gate" /etc/systemd/system/<app>.service` says 2) or named, with the reason, in
`Compose stacks`.

## Compose stacks Noust could not take over

A stack is waiting when the step cannot take it: Compose does not resolve its file **and** Docker does not
answer or the stack has no container to read what it was given from. `noust health` says so with the days it
has waited ("days waiting: 3"), the date does not move while the stack stays in that state, and from the
seventh day it is also a reason on its application in what needs attention. Nothing is changed for such a stack:
it starts as it always did, and the step tries again by itself every ten minutes, or at once with
`noust setup compose-gate --app DOMAIN`.

What mends it is what the reason says: make the compose file resolvable (`docker compose config` in its
directory prints what is wrong), start Docker, or start the stack so that there are containers to read.
Nothing needs the operator to touch Noust's own files.

## The image pull of before 3.2.1 leaves the unit

Until 3.2.1 the unit of a Compose stack ran `ExecStartPre=/usr/bin/docker compose [-p PROJECT] pull
--ignore-pull-failures` before every start. 3.2.1 took it out of the template: a new image of a database
downloaded at a restart recreated it with nobody deciding. A unit that nobody has deployed since still has the
line, and the step of 4.3 left it. The step of 4.4 **takes that one line out**: only that exact line, with or
without `-p`, and only in a unit that carries the `# Generated by Noust` line; a pull written differently, or any
line of a unit that is yours, is not touched. It runs `daemon-reload` and restarts nothing, says so in its
summary ("...and the line that pulled images at every start (before 3.2.1) taken out") and writes
`compose.pull_removed` in the audit trail with the unit and the line. Running it again changes nothing. A stack
that Noust has not taken yet keeps its unit exactly as it is until it does.

If your unit has an addition that empties `ExecStartPre=` (`<unit>.service.d/10-no-pull.conf`, written to avoid
that pull), the pull it avoided is gone from the unit's file now: delete the addition and run `systemctl
daemon-reload`, and the check runs in front of the start. Noust never deletes it for you.

## Rolling back

Going back to 4.3.0 needs nothing from this part of 4.4: the store has no new column for it, and a record that
was written from a stack's containers is read the same. A unit that lost the pull line does not get it back, and
4.3 does not need it. Going back past 4.3 is what [UPGRADING-4.3.md](UPGRADING-4.3.md#rolling-back) says
(`noust setup compose-gate --remove` first).
