# WASM 2.2 - Plan de ejecución

Fecha: 2026-09-28
Spec: `../specs/2026-09-26-wasm-2.2-design.md`. Parte de `2026-09-26-wasm-to-3.0-plan.md`.
Mandato: el dueño levantó la pausa el 2026-09-28 ("puedes continuar con el desarrollo hasta la
siguiente versión"): construir y publicar 2.2.0, y parar.

## Alcance

1. Blue/green (activación sin corte), opt-in por app, solo nginx en 2.2.
2. GitHub App por servidor (manifiesto, instalaciones, tokens por entorno, `/hooks/github`,
   estados de deploy, comentarios de preview, `wasm web expose-hooks`).
3. Previews por pull request (GitHub, GitLab, Gitea), cupo, TTL, borrado al cerrar.
4. Destinos de backup remotos con rclone; programaciones persistidas en el store (la retención
   de las programaciones, que hoy no se aplica, se aplica).
5. Notificaciones de deploy: inicio, éxito, fallo con la causa del health gate, vuelta atrás
   automática; también para los deploys del CLI.
6. Backlog 27: marcas manuales de secreto por variable y detección por valor.

## Decisiones

- Blue/green solo nginx en 2.2: Apache se rechaza con un error que lo dice.
- `wasm web expose-hooks DOMAIN` crea un sitio propio de WASM en un dominio dedicado que solo
  reenvía `/hooks/` a la consola en loopback; nunca edita el sitio de una aplicación.
- Previews en `pr-<n>-<app>.<dominio base>` (una sola etiqueta: un certificado comodín no
  cubre dos niveles). Pull requests desde forks: rechazados.
- Las programaciones de backup pasan al store; el timer ejecuta `wasm backup run-schedule`,
  que lee la programación, así la retención y los destinos se aplican de verdad. Los timers
  existentes se adoptan la primera vez que se listan.
- Notificaciones desde los eventos del recorder, no desde los jobs: así también las reciben
  los deploys del CLI y del webhook.
