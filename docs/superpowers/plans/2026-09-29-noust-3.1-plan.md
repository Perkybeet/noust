# Noust 3.1 - Plan de ejecución

> **Para agentes:** cada flujo se implementa con TDD (superpowers:test-driven-development): test que
> falla, implementación mínima, test que pasa. Este plan fija qué hace cada flujo, qué ficheros son
> suyos, las interfaces que comparte con los demás y cómo se acepta. El diseño detallado está en el
> spec y en el informe de investigación de cada flujo.

**Objetivo:** publicar Noust 3.1.0 con todo el backlog pendiente (ítems 22-52, ENS) y un sistema de
diseño normativo aplicado a toda la consola.

**Arquitectura:** oleadas de agentes en paralelo sobre la rama `dev/3.1`, con propiedad exclusiva de
ficheros; cada oleada termina con la verificación completa y un commit mío. Backend antes que la
consola que lo usa; el sistema de diseño antes que cualquier página.

**Stack:** Python 3.10-3.14 (FastAPI, Click, SQLite), React 19 + TypeScript + Vite + Tailwind v4 +
Base UI, Playwright, arnés Docker con systemd.

**Spec:** `docs/superpowers/specs/2026-09-29-noust-3.1-design.md` (prevalece sobre los informes).
**Informes:** `docs/superpowers/research/3.1/*.md` (detalle, órdenes exactas, fuentes).

## Restricciones globales

- Las cuatro reglas de `CLAUDE.md`: procesos solo por `CommandRunner` (argv, timeout, secretos por
  `env=`/`input=`); `except Exception` solo en una frontera de error y registrando; una implementación de
  cada cosa (la web es cliente de los managers); guardas en el punto de paso.
- Ninguna dependencia de runtime nueva salvo `python3-cryptography` (opcional, perezosa, declarada en
  `pyproject.toml`, `setup.py`, `obs/debian.control`, la spec RPM y las líneas de instalación de las
  puertas de release). Todo modelo de la API por `web/pydantic_compat.py` (pydantic 1.10 y 2).
- Nombres `wasm` que se conservan (cookies, cabeceras, `wasm_ro_`, `.wasm/`...): intactos.
- Copy de la consola: inglés y español, frases completas en los catálogos tipados de
  `panel/src/i18n`, sin fragmentos; la salida del sistema nunca se traduce ni se parafrasea.
- CSP estricta: nada de `style=` en markup, `<style>` inyectado, `innerHTML` ni librerías que los usen.
- Docstrings estilo Google en todo lo público; tipos modernos; errores accionables
  (`NoustError(..., details="cómo arreglarlo")`); comentarios que explican el porqué.
- Sin emojis en código, comentarios ni commits.

## Reglas de trabajo para los agentes (se copian en cada encargo)

1. Solo tocas los ficheros de tu flujo. Si necesitas cambiar uno ajeno, hazlo con `Edit` mínimo y
   dilo en tu informe; nunca reescribas un fichero ajeno con `Write`.
2. Nada de git que cambie estado (`commit`, `stash`, `checkout`, `reset`, `restore`, `clean`). Nada de
   sub-agentes ni forks. Nada de `uv run` en la raíz (destruye el `.venv`).
3. No regeneres artefactos compartidos: `panel/openapi.json`, `schema.gen.ts`, man pages,
   completions, `src/noust/web/static`. Consola: nunca `npm run build`; para regenerar
   `routeTree.gen.ts` usa `npx vite build --outDir /tmp/<tu-flujo>-build --emptyOutDir`.
4. Ejecuta solo tus tests, `ruff check`/`ruff format` sobre tus ficheros y `mypy` (Python), o
   `npx vitest run <tus rutas>`, `npx eslint <tus ficheros>`, `npx tsc -b` (consola). Node 22 en
   `~/.local/node22/bin`; venv en `.venv`.
5. Store: tu esquema va en tu fragmento de `src/noust/core/schema_v12.py` (solo tu constante);
   `tests/test_store_migrations.py::TestSchemaV12Migration` debe seguir pasando.
6. Rutas nuevas de la API: regístralas en `src/noust/web/permissions/routes_<área>.py` si el paquete
   existe; si no, lístalas en tu informe.
7. Eventos de auditoría: `noust.core.audit.record(...)` si existe; si no, usa el mecanismo actual de
   `web/api/audit.py` y dilo en tu informe.
8. Informe final (≤ 400 palabras): qué hiciste, ficheros, tests, qué queda y qué tocaste fuera.

## Foco de revisión

Entradas que el spec implica y que ningún test de flujo cubre por sí solo; cada una tiene su test en
el flujo dueño:

1. **Actualizar un servidor 3.0 en uso** (tokens existentes, sesión abierta, consola como servicio):
   nadie queda fuera, los tokens siguen valiendo y la consola pide crear la primera cuenta (B1, arnés
   `--upgrade`).
2. **Central 3.1 con nodos 3.0**: las vistas de flota muestran "no compatible" por nodo sin errores 500
   y las acciones masivas los saltan con motivo (B5b, E2E con un backend de versión vieja).
3. **Arreglos que pueden dejar fuera al operador con el túnel de la central abierto** (sshd,
   cortafuegos): la guarda los rechaza o se revierten solos (B3b, arnés de flota).
4. **Compilaciones que necesitan red, registros privados o escribir fuera del release** dentro del
   sandbox: error que dice qué y cómo, nunca vuelta silenciosa a root (B4, arnés).
5. **Español a 390 px**: textos largos que no desbordan, acciones de fila visibles, sin scroll horizontal
   de página (C0 contrato + capturas de cada flujo de la oleada 2).
